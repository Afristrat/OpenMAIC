# Incident — Exposition par sérialisation Coolify du 12 septembre 2026

Une commande de diagnostic a sérialisé un modèle Coolify complet au lieu de sélectionner uniquement des métadonnées non sensibles. Les identifiants concernés doivent être traités comme compromis.

Aucune valeur ne figure dans cet artefact. Les secrets de webhooks des trois applications Qalem ont été régénérés le 12 septembre 2026 par une mutation interne ne renvoyant aucune valeur. Les quatre enregistrements du jeton capture, historiquement stockés en clair et donc incompatibles avec le déchiffrement Coolify, ont été remplacés. Les huit enregistrements LTI des deux applications Qalem (prévisualisation et production, clé privée et clé publique), la paire VAPID Web Push et les clés internes de chiffrement LRS/pseudonymisation xAPI ont aussi été remplacés, après contrôle de zéro abonnement Push, zéro configuration LRS et zéro événement xAPI à préserver. Une première écriture employait un chiffrement Laravel sans sérialisation ; elle a été réencodée avant déploiement avec le format attendu par Coolify. La relecture bornée confirme désormais 28 enregistrements Qalem déchiffrables en chaînes non vides par Coolify, sans lire de valeur. Le LLM général, qui pointait encore vers un LAN privé, a été basculé vers le même proxy HTTPS que l’ASR et l’image après un contrôle API 200 de sa clé Qalem.

Le redéploiement coordonné est terminé : runtime au SHA `9a24e105e79638e46b97c6f0109c47e097ca0000` à 17:38:25 et web au même SHA à 17:51:37. Les deux workers et le web sont `healthy`, sans redémarrage ni OOM, et `https://qalem.ma/api/health` répond HTTP 200. Le premier essai web a révélé deux valeurs `SUPER_ADMIN_EMAILS` historiques stockées en clair. Elles ne sont pas des secrets mais empêchaient Coolify de déchiffrer l’ensemble de la configuration ; elles ont été réencodées en préservant leur contenu, sans le lire. Le contrôle final ne trouve plus aucune variable web indéchiffrable.

La clé Resend Qalem refuse l’inventaire des clés fournisseur avec HTTP 400 : aucune suppression ne peut donc être attribuée sûrement à Qalem plutôt qu’à un autre produit. Les clés fournisseurs restantes doivent être traitées avec leurs consommateurs avant révocation. Des recettes LTI, Web Push et xAPI, ainsi qu’une vérification de non-régression fonctionnelle, restent obligatoires après le redéploiement.

Prévention : les diagnostics Coolify doivent sélectionner explicitement des champs non sensibles et ne jamais sérialiser un modèle ou une relation complète.
